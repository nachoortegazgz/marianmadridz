## Cambios realizados en esta tanda

- **Wix Data:** `backend/dataAccess.js` pasa de importar `wix-data` a usar `items` de `@wix/data`; la elevación permanece centralizada en el adaptador. El mock offline se ajustó para usar el builder de consultas.
- **Wix Secrets:** se creó `backend/secretAccess.js`, que usa `@wix/secrets` + `auth.elevate` y devuelve `response.value` como string. Se migraron caja, inventario, webhooks, documentos fiscales, seguridad criptográfica y asistente IA. El código productivo ya no necesita `wix-secrets-backend`.
- **Bookings y Members:** el inventario del código actual ya utiliza `@wix/bookings` y `@wix/members`; no se ha encontrado un import productivo de `wix-bookings.v2` ni `wix-members-backend` en los módulos revisados.
- **Integridad fiscal:** la validación de hooks habilitada en el mock reveló que la caja no persistía `eventType` y que el cierre Z podía carecer de `traceId`. Ambos productores se han corregido en la rama. Los tests de ventas de mostrador declaran explícitamente `F2` cuando no aportan datos del destinatario.
- **Validación CI:** la suite offline del commit `0e8163a608aaf4a7aaf0596291d10d3e0572c16b` pasó; el gate de lint estaba todavía ejecutándose al redactar esta nota. Verificar el resultado final en la acción asociada al PR antes de fusionar.

## Migración pendiente por decisión de compatibilidad

- **Stores Catálogo V1 e Invoices V1:** mantener las versiones instaladas. No migrar a V3/V2 sin plan independiente, equivalencia funcional y pruebas de catálogo, inventario, checkout e impuestos.
- **APIs nativas de frontend Velo** (`wix-location-frontend`, `wix-window-frontend`, `wix-members-frontend`, `wix-pricing-plans-frontend`): no son deuda automáticamente; conservar mientras sean la API apropiada para Wix Editor.
- **Resend, OpenAI y servicio fiscal externo:** son integraciones externas, no APIs Wix que deban reemplazarse por el SDK de Wix. Mantenerlas en backend y bajo Secrets.
- **Cierre de migración total:** requiere completar la auditoría de todos los módulos, confirmar el gate CI verde en el commit final y ejecutar QA funcional en Wix (reservas simples/duales, permisos, caja y cierres). Ningún resultado offline certifica por sí solo el sitio publicado.

## 4. Bookings: prioridad alta

El flujo de reservas debe revisarse con especial cuidado.

### Componentes a migrar o validar

- Consulta de servicios.

- Consulta de disponibilidad.

```text

```

Además:

- Si el cliente selecciona profesional, debe utilizarse exactamente ese.

Una migración superficial puede conservar la interfaz, pero perder:

- Validación de conflictos.
- Selección correcta de profesionales.
- Estados `PENDING`, `RESERVED`, `PAID`, `CONFIRMED`, `CONFLICT`, `FAILED` y `COMPENSATED`.
- Compensación de la primera fase si falla la segunda.

## 10. Criterios para decidir si migrar

Migrar cuando:

- El SDK oficial cubre la misma operación.
- La API actual está obsoleta.
- Se mejora la autenticación.
- Se reducen llamadas manuales.
- Se obtiene tipado o validación mejor.
- Se mejora el mantenimiento.
- Se reduce el riesgo de endpoints incorrectos.

No migrar automáticamente cuando:

- El SDK no cubre toda la funcionalidad.
- El sitio utiliza Catálogo V1 y solo existe una solución V3 incompatible.
- La operación es estable y no está obsoleta.
- La migración puede alterar reservas o pagos.
- No existe una prueba de equivalencia.

1. Existe un SDK equivalente.
2. El comportamiento está documentado.
3. Las pruebas cubren la sustitución.
4. Se conserva la autorización.
5. Se valida el resultado en el sitio publicado.
