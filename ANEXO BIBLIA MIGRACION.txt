## 2. Matriz de módulos

| Dominio | Estado actual verificado | Decisión |
|---|---|---|
| CMS/Data | `backend/dataAccess.js` usa `@wix/data`; la elevación se mantiene centralizada. | Migración SDK aplicada. Hooks de integridad en `backend/data.js` se mantienen. |
| Bookings | El motor utiliza `@wix/bookings`, `bookingCore.js` y `bookingSaga.js`. | SDK ya aplicado. Mantener reserva dual como dos reservas simples F1/F2, coordinadas por `pairToken`; no usar Multiservice Booking. |
| Disponibilidad y creación | La disponibilidad y creación se gestionan por separado y la creación revalida disponibilidad nativa. | Mantener las pruebas de conflicto, concurrencia y compensación; requiere QA real Wix. |
| Members | El backend utiliza `@wix/members` para identidad de sesión. | SDK ya aplicado. No sustituir por módulos backend clásicos sin motivo documentado. |
| Secrets | `backend/secretAccess.js` usa `@wix/secrets` y `auth.elevate`; devuelve `response.value` como string. Consumidores: caja, inventario, webhooks, documentos fiscales, seguridad criptográfica y asistente IA. | Acceso centralizado; nunca devolver valores de secretos al frontend. |
| eCommerce | `@wix/ecom` se usa donde corresponde en checkout/pedidos. | Mantener separado de Bookings y del catálogo de tienda. |
| Wix Stores | La configuración del sitio corresponde a Stores Catálogo V1. | **No migrar automáticamente a V3**. Requiere plan independiente y pruebas de productos, variantes, stock y checkout. |
| Wix Invoices | El sitio tiene Invoices V1. | **No migrar automáticamente a V2**. Requiere estrategia y validación fiscal independiente. |
| Frontend Velo | Persisten APIs nativas como `wix-location-frontend`, `wix-window-frontend`, `wix-members-frontend` y `wix-pricing-plans-frontend` en páginas que las consumen. | Mantener cuando sean las APIs adecuadas para Wix Editor; no son deuda por sí solas. |
| Web methods | Los módulos backend usan `wix-web-module`. | Mantener para el entorno Wix Editor/Velo. |
| Integraciones externas | Resend, OpenAI y el servicio fiscal se llaman desde backend mediante HTTP. | No son APIs Wix; mantenerlas tras Secrets, validación, límites y control de errores. |

## 3. Correcciones adicionales de integridad

La activación de hooks reales en el mock offline reveló dos defectos de producción, corregidos en el mismo PR:

1. El productor de caja no persistía el `eventType` fiscal obligatorio. Ahora deriva el evento canónico a partir del tipo de movimiento o respeta el valor explícito validado por el hook.
2. El cierre Z podía iniciar sin `traceId`. Ahora genera uno si el llamador no lo proporciona.

Los tests de caja que representan ventas de mostrador sin datos del destinatario declaran `tipoFactura: "F2"`; los casos que requieren factura F1 deben proporcionar los datos fiscales del destinatario exigidos por el esquema.

## 4. Imports antiguos

No se detectan imports productivos activos de:

- `wix-data` en el adaptador CMS, que ahora importa `@wix/data`.
- `wix-secrets-backend` en los consumidores de secretos, que ahora usan `backend/secretAccess.js`.
- `wix-bookings.v2`; el motor usa `@wix/bookings`.
- `wix-members-backend`; el backend usa `@wix/members`.

Los mocks de pruebas pueden conservar adaptadores para simular APIs, pero no deben ser importados por código productivo.

## 5. Pendiente para cerrar el despliegue

La migración SDK del código revisado está fusionada y los gates offline están verdes. **La fase de producción no está certificada** hasta completar, sobre el sitio real y sin duplicarlo:

1. Sincronizar el proyecto Wix local con el commit de `main` usando Wix CLI autenticado.
2. Confirmar el diff de sincronización antes de publicar.
3. Probar reservas simples y duales, profesional elegido/automático, hueco de exposición, conflicto de slots, fallo de F2 y compensación.
4. Probar permisos CMS, caja, cierre Z, webhook y checkout con datos controlados.
5. Publicar solo tras superar esas pruebas y comprobar el comportamiento del sitio.

No se ha publicado el commit `ba1a32f` en Wix desde esta migración. El estado "Published" del sitio no demuestra que contenga este commit.

## 6. Regla de decisión

Migrar únicamente cuando la API SDK oficial cubra la operación actual y exista equivalencia verificable. No actualizar Stores V1 ni Invoices V1, ni retirar APIs nativas de frontend, sin una migración específica probada. No declarar la fase completa basándose únicamente en instalación de dependencias o tests offline.
